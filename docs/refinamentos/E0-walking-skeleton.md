## Debate (divergências e resolução)

1. **Divisão do E0c e reordenação do épico** (arquiteto propõe conformidade → E0c-CI → E0b → E0c-CD → E0d; SRE propôs split equivalente de jobs; QA pedia definição) → **consenso técnico entre os 5 agentes** (backend-dev validou esforço; QA teve suas 2 perguntas bloqueantes respondidas pela divisão). Fundamento: o CI é peça do gate híbrido de auditoria (roles.md §6.4) e não tem dependência externa; o deploy depende da VM Oracle (item 0, loteria de capacidade A1). **Como altera a estrutura do roadmap, precisa de aval do usuário (§6.14 — escalado, ver Conclusão).**
2. **Escopo do rascunho da task 0002** (rascunho previa 2 eventos fake `FilmCreated`/`FilmUpdated` + 2 queues) → **consenso: cortar** (anti-overengineering, roles.md §1). UM evento real (`catalogo.filme_criado`) emitido por via de escrita mínima com TX de verdade; DLQ declarada mas sem tooling de replay (doc.md §13: replay nasce com a saga no E6).
3. **Onde nasce o shell da SPA** (arquiteto o listou no E0c-CD; backend-dev recomenda E0c-CI por ser estático e desafogar a contagem de arquivos do CD) → **sem conflito de fundo**; decisão fica para a abertura do PRD do E0c-CI (backend-dev explicitou que não é bloqueante). Recomendação registrada: shell SPA no E0c-CI.
4. **Timeout de testcontainers RabbitMQ** (QA: 60-90s; backend-dev: 90-120s no runner ARM64, mais lento que dev local) → **consenso: 90-120s no CI**, wait strategy por log, sem sleep fixo (ADR 0006).
5. **Instrumentação OTel no E0b antes do SDK completo do E0d** (dependência invertida apontada pelo backend-dev) → **consenso:** E0b propaga `traceparent` usando só o pacote leve `go.opentelemetry.io/otel/propagation` (ou manualmente); SDK completo entra no E0d.

## Conclusão

- **Escopo final do épico:** E0 passa a ter 5 entregas restantes — **task de conformidade** (realinhamento package-by-domain, pré-E0b) → **E0c-CI** → **E0b** (task 0002 reescopada) → **E0c-CD** (assim que a VM existir; fura a fila se sair antes) → **E0d**. Pendente de aval do usuário (pergunta 1 abaixo).
- **Riscos priorizados:** (1) VM Oracle A1 não provisionada — única dependência externa do M1, capacidade é loteria (item 0 do roadmap, iniciar imediatamente); (2) flakiness testcontainers+RabbitMQ no runner ARM64 (mitigado: wait por log, 90-120s, container por pacote); (3) estouro de arquivos no E0c-CD se acumular SPA+deploy (mitigado: SPA no E0c-CI); (4) escopo do E0d inflar até virar E10 (mitigado: lista fechada — sem Tempo, 2-3 dashboards, 5 alertas).
- **Perguntas ao usuário (bloqueiam os PRDs afetados até resposta — §6.14.7):**
  1. **Aval para a reordenação do épico** (dividir E0c em E0c-CI/E0c-CD e sequência conformidade → E0c-CI → E0b → E0c-CD → E0d, atualizando o roadmap). Bloqueia: PRDs de E0b/E0c/E0d na nova ordem. Não bloqueia: task de conformidade (correção de drift contra ADR 0003 já aceito).
  2. **Autorização explícita para criar o ADR "Mensageria: RabbitMQ"** (roles.md §6.1; candidata já listada no doc.md §11 para "refinamento do E0/E6"). Escopo proposto: broker (com divergência registrada — decisão do usuário contra recomendação), topologia base (exchange topic única `morfeu.events`, routing key por domínio, quorum queues, `x-delivery-limit=3`, DLQ), contrato de entrega (outbox + publisher confirms + dedup na mesma TX), limites operacionais na VM (watermark/disk_free_limit), condições de reversão. Bloqueia: PRD da E0b (o ADR deve existir antes ou junto dele).
  3. **Item 0 (pré-bootstrap): quando começam as tentativas de criar a conta Oracle PAYG + VM A1?** Ação exclusiva do usuário; define o sequenciamento do E0c-CD. Não bloqueia PRDs.

## Exigências por task

### Task de conformidade (pré-E0b) — realinhamento package-by-domain

- Mover o catálogo para `internal/catalogo/` (layout ADR 0003: `handler.go`, `service.go`, `errors.go`, `queries.sql`, `db/` gerado); `cmd/app` → `cmd/morfeu` (composition root único); pacotes de plataforma explícitos (config, logger, cache, db).
- Ativar `depguard` no `.golangci.yml`: módulo não importa módulo; domínio não importa driver de infra direto.
- Ajustar `sqlc.yaml` (paths de geração por módulo) e Makefile; PRD lista explicitamente todos os arquivos movidos/renomeados.
- **Zero mudança de comportamento**: critério de aceite único = suíte da E0a passa sem alteração de asserts. Sem endpoint novo, sem feature.

### Task E0b (0002, reescopada) — outbox + RabbitMQ + worker idempotente

- Nasce package-by-domain. Fronteiras: outbox (tabela + `Enqueue(tx, evt)` + relay), cliente RabbitMQ e runtime do consumer (conexão/ack/dedup/shutdown) em **plataforma**; handler da mensagem no **domínio** consumidor. Nenhum domínio importa `amqp091-go` (depguard). Ownership excepcional das tabelas `outbox_events`/`processed_messages` (plataforma) documentado no PRD.
- **UM evento** (`catalogo.filme_criado`), UMA queue; sem `FilmUpdated`. Emissão por **subcomando CLI** do binário (stdlib `flag`, sem cobra, sem endpoint HTTP) que insere filme + evento **na mesma TX** via service real (`WithTx`).
- Relay: roda **só em `-mode=worker`/`all`** (nunca no `api`); polling 500ms–1s (LISTEN/NOTIFY registrado como otimização futura, não implementada); `SELECT ... FOR UPDATE SKIP LOCKED` na leitura; **publisher confirms síncronos** (`PublishWithDeferredConfirm` + `WaitContext` com timeout ~5s) — `published_at` só após confirm; reconexão manual (`NotifyClose` + backoff exponencial com teto, comportamento durante desconexão especificado no PRD).
- Envelope do evento: `message_id` (uuid), `event_type`, `aggregate_id`, `occurred_at`, `payload`, `traceparent` (header AMQP, propagator W3C via pacote leve `otel/propagation` — SDK completo só no E0d).
- Consumidor: dedup por `processed_messages` **na mesma TX do efeito**, via wrapper de plataforma; payload malformado → DLQ sem derrubar o processo; graceful shutdown por ctx (SIGTERM, timeout 30s, sem goroutine órfã).
- Topologia: exchange topic, **quorum queue**, `x-delivery-limit=3`, DLQ declarada; declaração idempotente no startup de todo processo que toca o broker, com parâmetros idênticos (evitar 406 PRECONDITION_FAILED). **Sem tooling de replay** (E6). Limpeza da tabela outbox = débito consciente registrado, fora do escopo.
- Compose: RabbitMQ `3.13-management-alpine` com `vm_memory_high_watermark` absoluto (~768MB) e `disk_free_limit` (~512MB) já em dev; 15672 nunca fora de `127.0.0.1`; healthcheck `rabbitmq-diagnostics -q ping` + `condition: service_healthy` no worker; credenciais via `.env` não versionado, senha forte, nunca `guest/guest`, nunca hardcode.
- Segurança: logs do relay/consumer nunca imprimem payload completo em `info` (só `event_type`, `aggregate_id`, `message_id`); princípio registrado: outbox nunca carrega segredo/PII no payload; `amqp091-go` registrado no `lib.md` com versão pinada + CVE checada na adição.
- Observabilidade (fonte do dado, sem dashboard): contador/query de `outbox_pendentes` exposto internamente para o E0d consumir.
- Testes (integração com testcontainers RabbitMQ real, `-race`): outbox-na-mesma-TX (rollback do efeito → evento não persiste); relay só marca `published_at` após confirm; broker fora do ar → evento permanece pendente e é reentregue (retry sem crash); dedup por estado final (mensagem 2× → efeito 1× + ack na 2ª); DLQ recebe mensagem envenenada sem travar a fila principal; shutdown sem perda/duplicação; `goleak.VerifyTestMain` no pacote do worker; migrations 002/003 up→down→up + `sqlc vet`; regressão: health/readiness ganha RabbitMQ sem quebrar contrato da E0a, `GET /filmes` intacto. Isolamento: container por pacote (TestMain) + filas/exchanges nomeadas por teste; wait por log (`Server startup complete`); sem sleep fixo.
- Estimativa: 13–17 arquivos. PRD trava: sem replay, sem métricas custom além do contador.

### Task E0c-CI — pipeline de CI + build ARM64 (peça de governança)

- Workflow `build-test` (gate de PR, roda sempre): `golangci-lint`, `go vet`, `go test -race ./...`, `govulncheck`, `sqlc vet`, gitleaks (diff completo, falha o job), job de migrations condicional por path (`migrations/` → up→down→up + sqlc vet), build `linux/arm64` → GHCR com tag por SHA + smoke do binário dentro do job (roda, não só builda). Runner ARM64 nativo (`ubuntu-24.04-arm`), sem QEMU; cache GHA no build Docker.
- O PRD deve **declarar a transição do gate híbrido** (roles.md §6.4): estes itens mecânicos substituem a parte mecânica da auditoria manual a partir do merge.
- Supply chain: todas as actions pinadas por **SHA completo** + Dependabot/Renovate para atualizar os pins; imagem base do Dockerfile pinada por digest; `GITHUB_TOKEN` com `permissions:` explícito (`packages: write`), sem PAT.
- Validação do pipeline: **PRs de prova descartáveis** demonstrando bloqueio real de cada gate (lint quebrado, data race injetada, CVE conhecida, SQL inválido, secret de teste, migration sem down; e migração de path: job de migrations não roda quando não toca `migrations/`).
- Testcontainers no CI: timeouts 90–120s (runner ARM64), wait por log. Suíte completa da E0a roda verde no runner real — falha por diferença de ambiente é bug do E0c-CI, não flaky.
- Auditoria pontual do histórico completo do repo (gitleaks full-history) antes do primeiro deploy real; achado → revogar/rotacionar (repo público: reescrever histórico não resolve).
- Recomendação registrada: **shell da SPA nasce aqui** (estático, sem dependência de VM; tokens de `docs/design/identidade-visual.md`, placeholder navegável, não produto) — confirmar na abertura do PRD.
- Estimativa: 6–9 arquivos (+5–8 se o shell SPA vier para cá).

### Task E0c-CD — deploy + Caddy/TLS + smoke (bloqueada pela VM Oracle)

- **Gate absoluto: hardening doc.md §14.5 completo antes do primeiro deploy público**, como checklist objetivo de merge: NSG só 80/443+22; **nenhum `ports:`** publicando PG/Redis/RabbitMQ/observabilidade no compose prod (15672 só via túnel SSH — explícito no PRD); senhas fortes geradas (distintas do dev) para PG/Redis/RabbitMQ via `.env` no host; SSH só chave; Caddy + Let's Encrypt + HSTS + `X-Content-Type-Options: nosniff` + `X-Frame-Options`/CSP básica no shell SPA.
- Deploy: workflow `deploy` separado (só push na main), **skip gracioso** se secrets da VM ausentes (log claro, não falha); chave SSH dedicada ed25519 sem passphrase só em Actions Secrets; `known_hosts` fixado (proibido `StrictHostKeyChecking=no`); usuário de deploy com **forced command** (`command=`, `no-pty`, `no-port-forwarding`, `no-agent-forwarding`) restrito ao script de deploy/rollback, sem sudo irrestrito.
- Compose prod separado (`docker-compose.prod.yml`); Caddyfile versionado montado por bind mount (troca de domínio sem rebuild); SPA e API no mesmo domínio.
- Smoke pós-deploy bloqueante contra a URL pública real (HTTPS): `GET /health` + `GET /filmes` (e readiness com RabbitMQ, pós-E0b); falha → rollback para imagem N-1 (via forced-command; validação manual controlada do rollback aceita — sem staging no budget R$ 0, ressalva do QA registrada). Rollback automatizado completo = overengineering (1 VM, dev solo); procedimento documentado.
- **Critério de aceite final da task = smoke verde na URL pública real**, não pipeline verde. Retenção de imagens GHCR documentada.
- Estimativa: 10–14 arquivos (6–8 se o shell SPA ficar no E0c-CI, como recomendado).

### Task E0d — observabilidade base (por último, consome E0b e E0c)

- OTel SDK completo (otelecho + otelpgx), sampling 10% + 100% erros, **exporter de traces noop/discard explícito** (não stdout verboso) — **sem Tempo** (E6/E10; qualquer tentativa de incluí-lo é escopo indevido). Instrumentação só via plataforma/middleware — domínio não conhece OTel.
- Métricas: app expõe `/metrics` (golden signals por rota roteada do Echo, nunca path bruto) + `outbox_pendentes`, lag do relay, profundidade DLQ (consumindo a fonte criada no E0b). Exporters (lista fechada): node_exporter, cAdvisor, postgres_exporter, redis_exporter, rabbitmq_prometheus (plugin nativo). Credenciais dos exporters com usuário de leitura mínima, via env.
- Cardinalidade: **proibido** label com seat/session/user id — critério de aceite com **teste estático** de labels.
- Logs: Alloy → Loki, retenção 14 dias E por tamanho (`limits_config`/compactor — disco é o recurso crítico); **infraestrutura de redação de campos sensíveis no logger nasce aqui** (senha, token, Authorization, PAN futuro) como item obrigatório do escopo, não débito.
- Grafana: provisionado por arquivo (datasources + dashboards versionados), **2–3 dashboards fechados** (golden signals API; USE da VM + PG/Redis/RabbitMQ; outbox/DLQ); sem senha literal em YAML versionado (env var interpolada); `GF_AUTH_ANONYMOUS_ENABLED=false`, `GF_USERS_ALLOW_SIGN_UP=false`; único serviço de observabilidade exposto (senha forte), resto rede interna.
- Alertas mínimos (lista fechada): disco>80% (nº 1), API down, erro>SLO, DLQ crescendo, consumidor parado, saturação de conexões PG — Grafana→Discord + watchdog externo gratuito.
- Compose de observabilidade em arquivo separado (`docker-compose.observability.yml`), incluído condicionalmente.
- Testes: integração leve (httptest + registry local) de golden signals + métricas de outbox no `/metrics`; correlação trace_id do log == trace_id do span; smoke declarativo do provisionamento Grafana (API retorna dashboard) — proporcional, sem suíte pesada; asserts da E0a inalterados.
- Estimativa: 16–20 arquivos. PRD trava: 2–3 dashboards, sem "mais um painel".
